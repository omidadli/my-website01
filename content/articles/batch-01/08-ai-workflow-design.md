## Article

### پاسخ کوتاه

یک AI Workflow خوب با انتخابِ مسئله شروع می‌شود، نه با انتخابِ ابزار. شش گام دارد: (۱) یک هدفِ قابل اندازه‌گیری تعریف کنید، (۲) فرآیند را روی کاغذ نقشه‌برداری کنید (ورودی، گام‌ها، استثناها، خروجی)، (۳) مرزِ قانون/مدل/انسان را مشخص کنید، (۴) ابزارها را با حداقل دسترسی وصل کنید، (۵) معیارِ کیفیت و روشِ نمونه‌برداری را تعیین کنید، (۶) مرحله‌ای مستقر کنید: shadow → محدود → مقیاس. بیشتر شکست‌ها در گام‌های ۲ و ۵ اتفاق می‌افتند، نه در مدل.

### گام ۱: مسئله را به هدف تبدیل کنید

صورت‌مسئلهٔ خوب این شکل را دارد:

> «الان برای [کار] حدود [X ساعت در هفته] وقت صرف می‌شود و [نرخِ خطا / زمانِ تأخیر] برابر [Y] است. می‌خواهیم بعد از ۳۰ روز این را به [Z] برسانیم.»

بدونِ این جمله، بعد از یک ماه نمی‌توانید بگویید موفق شدید یا نه. و اگر چند مسئله دارید، یکی را انتخاب کنید — ترجیحاً پرتکرارترینِ کم‌ریسک‌ترین.


پیش‌نیازِ این گام‌ها تصویرِ روشن از خودِ ایجنت است؛ اگر هنوز به آن مرحله نرسیده‌اید، [AI Agent چیست — راهنمای کامل](/blog/ai-agent-guide-business) را اول بخوانید. برای انتخابِ همان مسئله هم [پنج فرآیندِ مناسب برای شروع](/blog/ai-agent-business-processes) فهرستِ کوتاهِ خوبی جلوی رویتان می‌گذارد.

### گام ۲: نقشه‌برداری (مهم‌ترین گام)

فرآیند را با این پنج سؤال بنویسید:

1. **ورودی چیست و از کجا می‌آید؟** (فرم، ایمیل، چت، webhook، فایل اکسل)
2. **گام‌ها کدام‌اند؟** حداکثر ۵ تا ۸ گام؛ بیشتر از آن یعنی باید تقسیم شود
3. **استثناها کدام‌اند؟** برای هر گام بنویسید چه چیزی ممکن است خراب شود
4. **خروجی دقیقاً چیست؟** یک فایل؟ یک رکورد؟ یک ایمیل؟ با چه قالبی؟
5. **«درست بودنِ خروجی» را چطور تشخیص می‌دهید؟** این همان چیزی است که بعداً تبدیل به معیار می‌شود

اگر نتوانستید گام‌ها را بنویسید، مشکل از ابزار نیست — فرآیند هنوز تعریف نشده است.

### گام ۳: مرزِ قانون، مدل و انسان

برای هر گام تصمیم بگیرید چه کسی آن را انجام می‌دهد:

| نوعِ گام | مجری | مثال |
|---|---|---|
| شرطِ قطعی و عددی | قانون | اگر مبلغ > سقف، ارجاع به مدیر |
| تفسیرِ متن یا تصمیمِ چندحالته | مدل | تشخیصِ لحن و دستهٔ پیام |
| هر چیزِ برگشت‌ناپذیر یا حقوقی | انسان | تأییدِ بازپرداخت، ارسالِ قرارداد |
| بررسیِ نهاییِ کیفیت | انسان (نمونه‌برداری) | بازبینیِ ۱۰٪ خروجی‌ها در ماه اول |

قانونِ طلایی: مدل را در وسطِ جریان بگذارید، نه در انتهای آن. مدل برای تفسیر و پیش‌نویس عالی است؛ برای تصمیمِ نهاییِ بدون نظارت، نه.


و اگر هنوز مطمئن نیستید این مسیر اصلاً باید با ایجنت برود یا همان اتوماسیونِ سنتی کافی است، [کِی ایجنت و کِی اتوماسیون سنتی](/blog/ai-agent-vs-automation) همین تصمیم را با پنج سؤال روشن می‌کند.

### گام ۴: ابزار و دسترسی

برای هر ابزار سه چیز بنویسید: نام، سطحِ دسترسی (فقط‌خواندنی / نوشتن / نوشتن با تأیید)، و سقفِ استفاده در روز. اصلِ حداقلِ دسترسی را رعایت کنید: ایجنت فقط به چیزی دسترسی داشته باشد که برای انجامِ همان کار لازم است.

همچنین سه حصارِ فنی را از روز اول فعال کنید: سقفِ تعداد گام (مثلاً توقف بعد از ۱۰ تلاش)، سقفِ هزینهٔ روزانه، و kill switch (یک کلید برای خاموش کردنِ کل جریان).

### گام ۵: کیفیت و سنجش

قبل از استقرار، این چهار مورد را تعیین کنید:

- **عددِ پایه (baseline):** الان وضعیت چطور است؟
- **معیارِ اصلی:** یک عدد — نرخِ حل، زمان تا پاسخ، دقتِ دسته‌بندی، یا هزینهٔ هر خروجی
- **روشِ نمونه‌برداری:** در ماه اول، حداقل ۱۰٪ خروجی‌ها یا حداقل ۲۰ مورد در هفته توسط انسان بازبینی شود
- **آستانهٔ توقف:** اگر دقت از حدی کمتر شد، جریان خودکار خاموش و دستی شود


سنجشِ گامِ قبل بدونِ [زیرساختِ Tracking برای اندازه‌گیری درست](/blog/tracking-attribution-guide) همان حدسِ قشنگ است.

### گام ۶: استقرارِ مرحله‌ای

۱. **Shadow (سایه):** جریان اجرا می‌شود اما خروجی‌اش فقط ثبت می‌شود و تأثیری ندارد. در این مرحله دقت را روی نمونهٔ واقعی اندازه بگیرید.
۲. **محدود:** فقط روی یک بخشِ کم‌ریسک اجرا شود (مثلاً فقط دو دسته از تیکت‌ها).
۳. **مقیاس:** بعد از اینکه معیارِ اصلی به هدف رسید و دو تا چهار هفته پایدار ماند، گسترش بدهید.

بعد از استقرار، نگه‌داری را در تقویم بگذارید: بازبینیِ هفتگیِ نمونه‌ها، بررسیِ ماهانهٔ لاگِ خطاها، و به‌روزرسانیِ مستندات بعد از هر تغییرِ ابزار یا API.

### الگوی یک‌صفحه‌ای: Workflow Spec

این جدول را برای هر جریان پر کنید. اگر نتوانستید پر کنید، یعنی هنوز آمادهٔ ساخت نیستید:

| فیلد | مقدار |
|---|---|
| نامِ جریان | |
| هدف (یک جمله + عدد) | |
| مالک | |
| ورودی (منبع و قالب) | |
| گام‌ها (۵ تا ۸ مورد) | |
| مجریِ هر گام (قانون / مدل / انسان) | |
| ابزارها و سطح دسترسی | |
| استثناها و رفتارِ پیش‌فرض | |
| خروجی و قالب آن | |
| معیارِ اصلی و عددِ پایه | |
| روشِ نمونه‌برداری و آستانهٔ توقف | |
| حصارها (سقف گام، سقف هزینه، kill switch) | |

### یک مثال کامل: جریانِ پاسخ به درخواستِ قیمت

**هدف:** کاهشِ زمانِ اولین پاسخ به درخواستِ قیمت از ۶ ساعتِ کاری به کمتر از ۳۰ دقیقه، بدون کاهشِ نرخِ تبدیل به جلسه.

**ورودی:** فرمِ «درخواست مشاوره» + صفحاتِ بازدیدشدهٔ همان نشست.
**گام‌ها:**
1. قانون: اعتبارسنجیِ ایمیل و شماره (اگر نامعتبر → پرچم برای بررسیِ دستی)
2. مدل: تشخیصِ نوعِ درخواست (مشاوره / همکاری / استخدام / سؤالِ عمومی)
3. قانون: اگر «استخدام» یا «سؤالِ عمومی» → ارجاع به صندوقِ عمومی و خروج از جریان
4. مدل: خلاصهٔ دوخطی از نیازِ مشتری بر اساس فرم و صفحاتِ بازدیدشده
5. قانون: تعیینِ اولویت بر اساس اندازهٔ شرکت و بودجهٔ اعلام‌شده
6. ابزار: ارسالِ لینکِ تقویم متناسب با اولویت از طریق ایمیل
7. ابزار: ساختِ رکورد در CRM با خلاصه و اولویت
8. انسان: بررسیِ نهاییِ مواردِ اولویتِ بالا قبل از تماس

**خروجی:** ایمیلِ پاسخ + رکوردِ CRM با خلاصه و اولویت.
**معیار:** زمانِ اولین پاسخ، نرخِ تبدیلِ درخواست به جلسه، دقتِ دسته‌بندی.
**حصارها:** ارسال فقط برای دسته‌های «مشاوره» و «همکاری»؛ سقفِ ۵۰ ایمیل در روز؛ توقفِ خودکار اگر نرخِ خطای ارسال از ۲٪ گذشت.
**استقرار:** دو هفته shadow، دو هفته روی فقط دستهٔ «مشاوره»، بعد مقیاس.

### اشتباهات رایج

1. **پریدن مستقیم به مرحلهٔ اجرا.** مرحلهٔ shadow را رد نکنید؛ ارزان‌ترین راهِ کشفِ خطاست.
2. **تعریف نکردنِ آستانهٔ توقف.** بدون آن، افتِ کیفیتِ تدریجی را ماه‌ها بعد می‌فهمید.
3. **تغییرِ چند چیز با هم.** اگر همزمان مدل، دستورالعمل و ابزار را عوض کنید، نمی‌فهمید کدام تغییر اثر داشت.
4. **مستند نکردن.** بعد از سه ماه، کسی که مالکِ جریان است عوض می‌شود و دانش هم می‌رود.
5. **سنجشِ تعداد به‌جای نتیجه.** تعدادِ اجرا معیار نیست؛ کیفیت و اثر بر نتیجهٔ کسب‌وکار معیار است.

### جمع‌بندی

طراحیِ AI Workflow بیشتر «مهندسی فرآیند» است تا «هوش مصنوعی». مدل فقط یکی از اجزاست؛ چیزی که تعیین می‌کند جریان کار کند یا نه، وضوحِ فرآیند، مرزهای دسترسی، و انضباطِ سنجش است. اگر همین امروز یک کاری بکنید: یک فرآیند را انتخاب کنید و جدولِ Workflow Spec را برایش پر کنید — بیشترِ شفاف شدنِ مسیر در همین مرحله اتفاق می‌افتد.

## FAQ

### طراحی یک گردش‌کار چقدر طول می‌کشد؟

برای یک موردِ مستند و ساده، معمولاً یکی دو روز تا مرحلهٔ shadow و دو تا چهار هفته تا اجرای محدود. بخشِ زمان‌بر، یکپارچه‌سازی با سیستم‌ها و نوشتنِ استثناهاست، نه نوشتنِ دستورالعملِ مدل.

### به چه کسی نیاز داریم؟

سه نقش: یک مالکِ فرآیند (کسی که کار را از داخل می‌شناسد)، یک نفر برای یکپارچه‌سازی فنی، و یک بازبین که کیفیتِ خروجی را قضاوت کند. در تیم‌های کوچک این سه نقش می‌تواند روی دو نفر باشد، اما نباید روی یک نفر باشد.

### آیا باید همهٔ گام‌ها را خودکار کنیم؟

خیر. خودکارسازیِ ۷۰٪ِ میانی و نگه داشتنِ انسان در ابتدا و انتهای جریان، معمولاً بهترین نسبتِ ارزش به ریسک را می‌دهد.

### اگر مدل جوابِ اشتباه بدهد چه؟

دو لایه لازم است: جلوگیری قبل از وقوع (قالبِ خروجیِ مشخص، اعتبارسنجیِ خروجی با قانون، تأییدِ انسانی در گام‌های حساس) و کشف بعد از وقوع (لاگ، نمونه‌برداری، هشدار روی نشانه‌های غیرعادی).

### چطور بفهمیم وقتِ مقیاس دادن است؟

وقتی معیارِ اصلی به هدف رسیده باشد، حداقل دو تا چهار هفته پایدار مانده باشد، و نرخِ خطای کشف‌شده در نمونه‌برداری زیرِ آستانهٔ شما باشد. در غیر این صورت، مقیاس دادن فقط سرعتِ تولیدِ اشتباه را بالا می‌برد.
