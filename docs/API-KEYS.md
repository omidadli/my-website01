# کلیدهای API — ۵ اسلات برای هر بخش

این سند دقیقاً همان چیزی است که برای «فعال‌کردن هوش مصنوعی سایت» لازم است:
هر بخشی از سایت که کلید API می‌خواهد، **۵ اسلات کلید** دارد. کلیدها فقط در
پنل ادمین وارد می‌شوند (هیچ کلیدی در کد یا در مخزن Git نیست)، و سیستم به‌صورت
**خودکار** از کلید بعدی استفاده می‌کند و **چت قبلی را مرور می‌کند** تا گفتگو
طبیعی ادامه پیدا کند.

> خلاصه‌ی یک‌خطی: `پنل ادمین → دستیار و لیدها → کلیدهای API`
> → بخش را انتخاب کن → ۵ کلید را وارد کن → «ذخیره‌ی ۵ کلید».

## ۱. کدام بخش‌های سایت کلید می‌خواهند؟ (۶ بخش × ۵ کلید = ۳۰ اسلات)

| # | بخش (`sectionId`) | کجا مصرف می‌شود | کلید محیطی (آخرین گزینه) |
|---|-------------------|------------------|---------------------------|
| ۱ | `site-assistant` | دستیار هوشمند سایت (ویجت چت + ماسکوت) — با RAG روی مقالات | `GEMINI_API_KEY` |
| ۲ | `seo-slug` | تولید اسلاگ انگلیسیِ سئو از عنوان فارسی (فقط ادمین) | `GEMINI_API_KEY` |
| ۳ | `business-therapist` | محصول «تراپیست بیزینسی و منتور مارکتینگ» | `GEMINI_API_KEY` |
| ۴ | `growth-path` | محصول «مسیرساز توسعه فردی» | `GEMINI_API_KEY` |
| ۵ | `problem-solver` | محصول «راه‌حل‌یاب» | `GEMINI_API_KEY` |
| ۶ | `mock-customer` | محصول «مشتری فرضی» | `GEMINI_API_KEY` |

اسلات‌های ۱ و ۲ پیش‌فرض روی **Google Gemini** و اسلات‌های ۳ تا ۵ روی مسیر
**OpenAI-سازگار** تنظیم شده‌اند تا اگر همه‌ی کلیدهای Gemini لیمیت خوردند،
سرویس‌دهنده‌ی دیگری هم در دسترس باشد. هر اسلات را می‌توان آزادانه به
Gemini / OpenAI / هر پروکسی سازگار با OpenAI (OpenRouter، پروکسی‌های ایرانی و …)
تغییر داد؛ فقط `Base URL` و `Model` را همان اسلات پر کن.

## ۲. وضعیت محصولات: فقط کلید لازم است

هر ۴ محصول هوشمند کاملاً کدنویسی شده‌اند و بدون هیچ تغییری آماده‌ی فروش‌اند؛
تنها چیزی که کم دارند کلید API است:

| مورد | وضعیت |
|------|-------|
| تعریف محصول (نام، تگلااین، توضیح، مخاطب، آیکون، رنگ) | ✅ `lib/tools.ts` + `src/data/tools.ts` |
| سیستم‌پرامپت اختصاصی هر محصول | ✅ ۷۷۰ تا ۸۶۰ کاراکتر برای هر محصول |
| پیام خوش‌آمد + ۴ سوال پیشنهادی + placeholder | ✅ |
| صفحه‌ی محصول و دمو (`ProductDetailPage` / `PRODUCT_DETAILS`) | ✅ |
| پلن‌های قیمت‌گذاری (۳ پلن برای هر محصول) | ✅ `lib/toolPlans.ts` |
| قفل دسترسی (شماره موبایل + کد اختصاصی + دستگاه) | ✅ |
| سکه‌ی طلایی هدیه و سهمیه‌ی پیام | ✅ |
| پاسخ محلیِ بدون کلید (نمایشی) | ✅ `localToolAnswer` |
| **کلید API** | ⬜ باید در پنل ادمین وارد شود |

این موارد با تست خودکار بررسی می‌شوند:

```bash
npx tsx scripts/ai-keys.test.ts     # یا npm test
```

## ۳. چرخش خودکار کلیدها (Auto-Failover)

ترتیب امتحان کلیدها در هر درخواست:

1. **کلیدِ همین گفتگو** (Sticky): کلیدی که آخرین بار همین مکالمه را جواب داده —
   تا بی‌دلیل جابه‌جا نشویم.
2. **کلیدهای سالم** به ترتیب اسلات: ۱ → ۲ → ۳ → ۴ → ۵.
3. **کلیدهای کول‌داون‌دار** (لیمیت‌خورده): نزدیک‌ترین به زمان آزادشدن.
4. **کلید محیطی** (`GEMINI_API_KEY`) اگر تنظیم شده باشد.
5. اگر هیچ‌کدام جواب نداد: پاسخ محلیِ بدون هزینه (سایت هرگز «خطا» نشان نمی‌دهد).

تشخیص خطا و مدت کول‌داون:

| خطا | تشخیص | کول‌داون | نتیجه |
|-----|-------|----------|-------|
| Rate Limit (429، `RESOURCE_EXHAUSTED`) | `rate_limit` | ۱۵ دقیقه | کلید بعدی |
| سهمیه/اعتبار تمام‌شده (`insufficient_quota`, billing) | `quota` | ۶ ساعت | کلید بعدی |
| کلید نامعتبر (`401/403`, `API key not valid`) | `auth` | ۲۴ ساعت | کلید بعدی |
| خطای سرور (5xx) | `server` | ۲ دقیقه | کلید بعدی |
| تایم‌اوت / شبکه | `timeout` / `network` | ۱ دقیقه | کلید بعدی |
| پاسخ خالی | `empty` | ۵ دقیقه | کلید بعدی |
| درخواست بد (پرامپت/فیلتر محتوا) | `bad_request` / `blocked` | — | چرخش متوقف می‌شود (کلید بعدی فایده ندارد) |

پنل ادمین برای هر اسلات این‌ها را نشان می‌دهد: سلامت (`سالم` / `لیمیت‌خورده` /
`نامعتبر` / `خطا`)، شمارش معکوسِ کول‌داون، تعداد موفق/خطا/لیمیت/جابه‌جایی،
آخرین زمان استفاده، آخرین تأخیر (ms) و آخرین پیام خطا. دکمه‌ی
«صفر کردن کول‌داون‌ها» همه‌ی وضعیت‌ها را فوری پاک می‌کند.

## ۴. ادامه‌ی طبیعی گفتگو پس از تغییر کلید

پیش از هر پاسخ، سرور این کارها را انجام می‌دهد:

1. **حافظه‌ی گفتگو**: پیام‌های قبلیِ همان مکالمه از جدول `ai_chat_memory`
   خوانده می‌شود (کلاینت یک `sessionId` پایدار می‌فرستد؛ در
   `localStorage` نگه داشته می‌شود و بعد از ۳ روز بی‌فعالیتی خودش نو می‌شود).
2. **ادغام با تاریخچه‌ی کلاینت**: تکراری‌ها حذف و حداکثر ۲۴ پیام آخر فرستاده می‌شود.
3. **دستور پیوستگی**: اگر پاسخ روی کلید دیگری بیفتد، به مدل گفته می‌شود که
   مکالمه را مرور کند، لحن و مسیر را حفظ کند و **هرگز** به تغییر سرویس/کلید
   اشاره نکند:
   > «این گفت‌وگو از قبل در جریان است… مکالمه‌ی قبلی را مرور کن… از صفر شروع نکن…
   > هرگز به تغییرِ سرویس، مدل، کلید یا زیرساختِ پاسخ‌دهی اشاره نکن.»
4. **ثبت در حافظه**: پرسش و پاسخ جدید (حتی پاسخ محلی) ذخیره می‌شود تا نوبت بعد
   از همان‌جا ادامه پیدا کند.

نتیجه: کاربر یک دستیارِ واحد و پیوسته می‌بیند؛ لیمیت‌خوردن کلیدها فقط در
سرعتِ پاسخ نمود دارد، نه در کیفیت گفتگو.

## ۵. API مدیریت کلیدها (برای ابزارها/اتوماسیون)

```
GET  /api/tools?view=settings     → { ok, sections:[ { sectionId, name, keys:[5], activeKeyId, healthyCount, configuredCount, totalKeys, envKeyPresent } ], items:[…legacy…], keysPerSection: 5, sectionsMeta:[…] }   (ادمین)
GET  /api/tools?view=keyEvents    → { ok, items:[ { section_id, key_id, code, status, message, created_at } ] }                                                                                                       (ادمین)
POST /api/tools { action:"setProductKeys" | "setSectionKeys", sectionId, keys:[5×{ id, label, provider, baseUrl, model, apiKey?, enabled?, clearKey? }] }                                                              (ادمین)
POST /api/tools { action:"setKey",   sectionId, keyIndex (0..4), provider, model, baseUrl, apiKey? }                                                                                                                  (ادمین)
POST /api/tools { action:"testKey",  sectionId, keyIndex (0..4), [provider, model, baseUrl, apiKey] } → { ok, latencyMs, model, reply }                                                                                (ادمین)
POST /api/tools { action:"testAllKeys", sectionId } → { ok, results:[5], passed, total }                                                                                                                             (ادمین)
POST /api/tools { action:"resetKeyState", sectionId, [keyIndex] }                                                                                                                                                     (ادمین)
POST /api/tools { action:"clearKey", sectionId, [keyIndex] }   // بدون keyIndex = پاک کردن همه‌ی ۵ کلید                                                                                                                (ادمین)
```

قواعد مهم:

- `apiKey` خالی یا **ماسک‌شده** در ورودی = «بدون تغییر» (کلید ذخیره‌شده حفظ می‌شود).
- `clearKey: true` فقط همان اسلات را پاک می‌کند.
- کلیدها **هرگز** کامل برنمی‌گردند؛ فقط `keyMask` (مثلاً `AIza••••3456`).
- برای هر بخش، `sectionId` معتبر است (`site-assistant`، `seo-slug` و ۴ محصول).
- `productId` قدیمی هم پذیرفته می‌شود (سازگاری با نسخه‌های قبلی).

پاسخ عمومی چت‌ها هم — برای پایش — شماره‌ی اسلاتی که جواب داده را برمی‌گرداند:

```jsonc
// POST /api/tools { action: "chat", productId, deviceId, sessionId, messages }
{ "ok": true, "answer": "…", "mode": "ai",
  "key": { "slot": 2, "label": "کلید ۲", "provider": "gemini", "switched": true, "recalled": 4, "attempts": 2 } }
```

## ۶. ذخیره‌سازی

| کجا | جدول / فایل | محتوا |
|-----|-------------|-------|
| Production (Cloudflare D1) | `ai_section_keys` | ۵ کلید هر بخش (JSON، فقط سرور) |
| Production | `ai_key_state` | سلامت، کول‌داون، شمارنده‌های هر اسلات |
| Production | `ai_chat_memory` + `ai_chat_session` | حافظه‌ی گفتگو + کلیدِ جاری هر مکالمه |
| Production | `ai_key_events` | رویدادهای لیمیت/جابه‌جایی |
| Development | `.dev-ai-keys.json`, `.dev-ai-states.json`, `.dev-ai-memory.json`, `.dev-ai-sessions.json`, `.dev-ai-events.json` | همان‌ها برای اجرای محلی |

جدول‌ها در اولین درخواست خودکار ساخته می‌شوند (`ensureCoreTables`)، پس اجرای
دستی migration لازم نیست؛ ولی برای شفافیت و نصبِ تکرارپذیر، هر ۵ جدول و هر دو
ستونِ `chat_messages` داخل `schema.sql` و در فایل مستقل
`migrations/0005_ai_section_keys.sql` هم آمده‌اند:

```bash
# فقط روی دیتابیسِ موجود (نصبِ از صفر با schema.sql کامل است)
npx wrangler d1 execute omidadli01-site-db --remote --file=./migrations/0005_ai_section_keys.sql
```

> اگر API قبلاً جدول‌ها را خودکار ساخته باشد، دو دستور `ALTER TABLE` انتهای این
> فایل خطای «duplicate column name» می‌دهند که بی‌خطر است (بقیه‌ی دستورها
> `IF NOT EXISTS` هستند).

فایل‌های `.dev-ai-*.json` در `.gitignore` هستند و هرگز commit نمی‌شوند.

## ۷. راه‌اندازی گام‌به‌گام (۵ دقیقه)

1. کلیدها را از [Google AI Studio](https://aistudio.google.com/apikey) (برای
   Gemini) یا پنل OpenAI/پروکسی بگیرید.
2. وارد `پنل ادمین → کلیدهای API` شوید و بخش را انتخاب کنید.
3. برای هر اسلات: سرویس‌دهنده، مدل، `Base URL` (فقط برای OpenAI-سازگار) و کلید
   را وارد کنید و «ذخیره‌ی ۵ کلید» را بزنید.
4. با دکمه‌ی «تست» (هر اسلات) یا «تست همه‌ی ۵ کلید» اتصال را زنده بسنجید؛
   تأخیر (ms) و پاسخ کوتاه مدل نمایش داده می‌شود.
5. برای هر ۶ بخش همین کار را تکرار کنید (چت دستیار، اسلاگ سئو و ۴ محصول).
6. یک پیام در همان بخش بفرستید و در «رویدادهای کلیدها» ببینید چه کلیدی جواب داده
   و آیا جابه‌جایی رخ داده است.

> اگر می‌خواهید همه‌ی بخش‌ها به‌صورت پشتیبان از یک کلید محیطی استفاده کنند،
> فقط `GEMINI_API_KEY` را در Secrets کلودفلر تنظیم کنید؛ ولی توصیه‌ی ما پر کردن
> ۵ اسلات است تا لیمیت یک کلید، سایت را متوقف نکند.

### چک‌لیست اعتبارسنجی

```bash
npm run lint && npm run lint:functions && npm test && npm run build
```

- `npm test` شامل `scripts/ai-keys.test.ts` است که کامل‌بودن ۴ محصول، ۵-اسلاتی
  بودن هر بخش، چرخش خودکار روی خطای ۴۲۹، کول‌داون‌ها و ادامه‌ی گفتگو را تست می‌کند.

## ۸. پرسش‌های پرتکرار

**آیا با تمام‌شدن کلیدها سایت می‌خوابد؟**
نه. سایت به پاسخ محلیِ بدون هزینه برمی‌گردد (`mode: "local"`) و فقط در پنل ادمین
دیده می‌شود که کلیدها لیمیت خورده‌اند.

**اگر کلید اشتباه وارد شود چه می‌شود؟**
در تست کلید، خطای دقیق نمایش داده می‌شود؛ در چت واقعی کلیدِ نامعتبر ۲۴ ساعت
کول‌داون می‌گیرد و بقیه‌ی اسلات‌ها امتحان می‌شوند.

**آیا می‌توانم مخلوطی از Gemini و OpenAI داشته باشم؟**
بله، هر اسلات مستقل است (سرویس‌دهنده/مدل/Base URL جدا).

**حافظه‌ی گفتگو چقدر ذخیره می‌شود؟**
۸۰ پیام آخر هر مکالمه؛ پیام‌های قدیمی‌تر خودکار پاک می‌شوند.

**آیا کلیدها به مرورگر می‌روند؟**
فقط نسخه‌ی ماسک‌شده (`AIza••••3456`) برای نمایش وضعیت. درخواست‌های مدل همیشه
سمت سرور انجام می‌شوند.
